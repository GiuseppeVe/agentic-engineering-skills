# Ask Matt

Recommend the next skill or flow for the user's situation. A flow is a path through skills; this map is orientation, not an installation inventory or permission to execute the route.

## Route against the current environment

1. Check the current runtime's available skill catalog. Names below describe the original suite; availability and invocation rules come from the current environment.
2. Before stating what a skill does, recommending it, or recommending a step be skipped, read its `SKILL.md`. If a mapped skill is unavailable, report that gap. Inspect an available candidate's instructions before suggesting it, and explain any missing behavior rather than treating names as aliases.
3. Give the next route and why it fits. User-invoked skills are suggestions for the user to invoke; routing alone does not launch implementation, setup, or publication. Follow existing scope and permissions for any separately requested action.

## Main flow: idea → ship

| Situation | Route |
| --- | --- |
| Sharpen an idea | In a working directory, `/grill-with-docs` interviews while retaining domain language in `GLOSSARY.md` and decisions in ADRs. Without a working directory, `/grill-me` gives the same interview statelessly. Both wrap `/grilling`, the primitive also used by triage, wayfinder, and architecture surveys. Reach for the primitive directly when an unwrapped interview is wanted. |
| A design question needs runnable evidence | `/handoff` out to a fresh session in a separate prototype directory → `/prototype` → `/handoff` findings back to the original thread. Prototype answers one state, business-logic, or UI question with throwaway code. Keep it as a primary source on `prototype/<name>` from main, linked from the implementation issue; fold the answer into real code. Throwaway describes how it is written, not automatic deletion. |
| Build fits one session | `/implement` in the current context. |
| Build spans sessions | `/to-spec` synthesizes the thread, then `/to-tickets` creates self-contained tracer-bullet tickets with blocking edges. Work blockers-first with `/implement` per ticket and `/clear` between tickets, or use `/implement-spec` to run the task graph's ready frontier through parallel implementers on one integration branch. Local tickets live under `.scratch/<feature>/issues/`; real trackers use native blocking links. |
| Build and verify each behavior | `/test-driven-development` drives one red-green slice at a time. `/implement` runs it and `/code-review` per ticket; `/implement-spec` implementers drive it, then review the integration branch once. Code review checks Standards + Spec against a fixed point. Both skills also stand alone: TDD for a concrete behavior without a full spec, review for a branch or PR. |
| Write a PR | Model-invoked `/pr` shapes the body around the smallest useful visual, before/after evidence, and a one-way/two-way door call. |
| Learn from a build | `/retro` proposes environment improvements: navigation, deterministic checks for mechanical mistakes, coding standards for judgement calls, steering files, and tools. Run it in the session being reviewed before clearing; after clearing, supply that session's log. |

### Context and phase boundaries

Keep idea sharpening through `/to-tickets` in one context so reasoning survives into the spec and tickets. Each per-ticket implementation starts fresh. If context approaches the smart-zone limit before ticketing, compact at the nearest phase boundary rather than push through degraded reasoning.

For any context-switch decision, read [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md): apply its ordered tree at a phase boundary, with Continue first and compact last. Mid-phase, continue or split remaining work into scoped subagents. It defines when clear, portable handoff, subagent, and compact earn their context cost; use current harness capabilities and permissions.

## On-ramps and codebase health

| Starting situation | Route and handoff |
| --- | --- |
| Raw incoming bugs or requests | `/triage` moves issues through roles into agent-ready issues for implementation. Tickets generated by `/to-tickets` are already ready and bypass triage. |
| Hard bug, intermittent flake, or regression | `/diagnosing-bugs` first establishes one tight command already red on this bug, then fixes with a regression test. Follow with `/retro`; a missing seam for locking behavior down becomes architecture work. |
| Huge, foggy effort beyond one session | `/wayfinder` resolves a shared tracker map of decision tickets, producing decisions rather than deliverables. Once clear, hand off to `/to-spec` to collapse linked decisions into a buildable plan, then ticket and implement. Direct implementation fits only when the effort proves genuinely small. Use ordinary idea sharpening for well-scoped work. |
| Survey architecture for upkeep | `/improve-codebase-architecture` finds deepening opportunities. A chosen candidate becomes an idea for the main flow; `/codebase-design` supplies the module-design vocabulary. |

## Standalone and vocabulary

| Need | Skill |
| --- | --- |
| Domain terms or durable decisions | Model-invoked `/domain-modeling`: resolve fuzzy or overloaded language and record hard-to-reverse decisions as ADRs. It supplies the vocabulary discipline used by the documented interview. |
| Module shape and test seams | Model-invoked `/codebase-design`: deep-module vocabulary—module, interface, depth, seam, adapter, leverage, locality—used by TDD and architecture surveys. |
| Reading legwork | `/research` uses a background agent and primary sources to leave a cited Markdown file in the repo while work continues. Findings feed idea sharpening. |
| Information held by someone else | `/to-questionnaire` interviews the user about recipient and needed answers, then writes questions for that gap. Responses feed idea sharpening or specification. |
| Steps only a human can perform | Model-invoked `/wizard` generates an interactive bash procedure for infrastructure, credentials, CI secrets, dashboards, or cutover: open URLs, capture values, write `.env`/GitHub secrets. Use only where human involvement is necessary; agents perform actions they can do themselves within authorization. |
| Explanation did not land | `/wait-what` re-pitches the last message in plain language using `GLOSSARY.md`; usable mid-conversation inside another flow. |
| Learn a concept across sessions | `/teach` uses the current directory as a stateful workspace. |
| Write agent-consumed documents | `/writing-for-agents` covers skills, steering files, and pointed-at docs. |

Before the first engineering flow, inspect the existing tracker, triage labels and document layout. Any configuration or credential changes require authorization.
