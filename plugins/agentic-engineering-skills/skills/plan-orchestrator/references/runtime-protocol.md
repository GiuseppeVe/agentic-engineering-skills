# Runtime Protocol

## Setup and run state

Verify the plan, spec and any supplied contracts map, including revisions. Record authority separately for task commits, PR creation, push, and integration/merge. Missing task-commit authority does not block implementation dispatch: implementation remains uncommitted. Before a reviewer creates a commit, verify that authority or stop at a reviewed uncommitted state and report the exact gate. An implementation assignment alone does not grant commit authority.

Choose workspaces before dispatch. A sequential run may use one run branch and worktree. Concurrent independent tasks require isolated task workspaces, disjoint ownership and a defined integration order; never allow concurrent mutation of one worktree. Record the starting revision and workspace reference passed to each child. Pending workspace setup blocks only tasks that need that workspace; definitive inability to provide a safe workspace blocks those tasks.

Use task results and verified Git state as the normal run record. Keep a non-versioned ledger only when the run is long, resumable, externally coordinated or too concurrent to reconstruct safely. A ledger records task dependencies, workspaces, child identities, accepted commits, required REQs and checkboxes, evidence, assumptions and blockers; it does not require a universal queue, `current_task`, provisional IDs or transition log. On resume, reconcile any ledger with host status and Git before dispatch.

## Dispatch and verification

Select a task only when its declared dependencies are accepted and its recorded base and workspace contain their exact accepted state. Acceptance on another branch or as an uncommitted reviewed diff is not enough: materialize each dependency through its reviewed commit or exact reviewed diff, then verify the resulting commit or tree in the dependent task workspace before dispatch. Default to one active task when workspace isolation, ownership or integration order is unclear. Independent ready tasks may run concurrently only when their workspaces and mutation scopes are isolated. Never parallelize tasks merely because the plan does not state a dependency; verify disjointness first. If the host cannot create a required child, report that task `BLOCKED`.

A queued ID or progress update is not completion. Follow up in the same thread when evidence is missing. Do not start the reviewer for a task while its implementer can still mutate that task workspace. If children conflict over a workspace or scope, suspend affected mutation and integration until reconciled. Record failures or stops; replace a child only after confirming it cannot still modify its workspace.

Advance a task from implementation to review only after the implementer's turn ends, its role-specific evidence is verified, and no work can still modify its workspace. Verify the base SHA, branch, worktree diff and checks; the implementation result remains uncommitted. After review, verify the final reviewed diff and, when authorized and required, its task commit.

Classify evidence by purpose. `process` evidence records how the change was developed, such as an observed TDD RED; it must identify the pre-fix revision or reproducible state, command, expected behavioral failure and observation time, and it need not match the final commit. `final_state` evidence proves acceptance, such as GREEN/regression tests, lint, typecheck and review checks; it must identify the final reviewed commit or exact uncommitted diff and be rerun after the last relevant fix. Earlier final-state evidence is stale. A historical RED cannot by itself prove final correctness, and rerunning RED on the fixed commit is not required. A session may remain open; request shutdown during final cleanup.

## Subthread assignments

For each child, pass the task ID, required references and exact assigned task workspace. Require the [shared result contract](../../task-implement/SKILL.md#completion): `outcome`, `satisfied_requirements`, `open_requirements`, `checks` and the other evidence and context fields defined there. Do not paste source, child-skill internals or implementation strategy into the assignment.

- **Implementation:** invoke `task-implement` with the host-native skill command and provide exactly three task inputs: plan path, spec path, and exact instruction identifying the selected task. Read the first five lines of the invoked skill's body after its frontmatter to select orchestrator and subagent models and effort. It implements only that plan task and may dispatch subagents for implementation subtasks within its scope. It leaves changes uncommitted and reports implementation facts and evidence using the shared result contract. Verify the diff, branch and worktree, and confirm no work can still modify it before proceeding.
- **Review:** after implementation verification, create a separate subthread on the same task workspace. Build a clean-room packet from the original task instruction, any parent- or owner-approved task amendments, plan/spec paths, exact diff and objective command evidence. Exclude the implementer's outcome, requirement-satisfaction claims, assumptions, deviations, self-assessment and any prior verdict; an authoritative amendment comes from the parent or owner, not from the implementer's report. Invoke `test-driven-development` with the host-native skill command. The reviewer verifies task criteria, fixes in-scope findings and returns the shared result contract. Delegate task-commit authority only when already granted; otherwise the reviewer must leave the reviewed result uncommitted and identify the exact diff. When a commit is authorized and required, verify that it contains the reviewed workspace state before deciding acceptance. Use `agent-architecture-audit` for architecture-sensitive tasks when available; record a gap if unavailable, blocking only when required by the plan.

Coordinate any fixes within the same task lifecycle. Never expand into another task. Honor model/effort stated in the opening lines of `task-implement` and higher-priority host instructions; record effective supported settings.

## Acceptance and completion

The orchestrator decides acceptance from the implementer's and reviewer's outputs, the task criteria and verified evidence. A delivery manifest or `manifest check` establishes delivery consistency only; it does not prove semantic success. Preserve a `partial` outcome as partial: human authorization to proceed is neither a waiver nor evidence that requirements are satisfied. A blocker or missing required evidence prevents `ACCEPTED`; a `complete` report with required unverified items is partial and rejected for acceptance. Record unverified items outside required criteria without blocking acceptance.

Accept a task only when every REQ required of that task is satisfied with appropriate evidence. A gap may remain for a named later task only when the plan explicitly assigns it there and it is not a closure criterion of the current task; verify and record that plan basis. The REQ remains globally open until satisfied. An implementer, reviewer or owner instruction to proceed cannot reassign it ad hoc. Mark a REQ `not applicable` only with an explicit basis in the spec or plan. Keep rejected or partial tasks open and coordinate the missing work in their lifecycle.

Complete the plan only after every required spec/plan REQ is closed with evidence or a supported `not applicable` decision, every required checkbox is closed, and every task is accepted. An open deferred REQ or required checkbox prevents plan completion.

## Integration and closeout

After each review, verify the final reviewed state and decide acceptance under the criteria above. If an integration target is provided, integrate only exact accepted commits or verified diffs, in dependency order, without replacing remote work and with authority for that target. Require explicit human authorization for main; divergence or non-fast-forward is `BLOCKED`, with no force-push or reset. Verify the target SHA. Failed integration blocks dependants of that task, not unrelated isolated work. After every plan task is accepted and plan completion criteria are met, open the plan's PR only if assigned and authorized, then follow the repository's review, gate, merge and cleanup rules on that exact head. The PR is plan-level, not task-level. If PR creation is unassigned or unauthorized, report local readiness and the omission; this alone does not make the plan incomplete. Integration and merge require their own authority. If no integration target is assigned, record the omission and accept locally.

If the assignment includes a PR, follow the repository’s review, gate, merge and cleanup rules on the exact head. For a map-master assignment, report readiness and wait for its merge go-ahead. Complete the authorized merge and cleanup; report any unfinished cleanup and do not remove a worktree while outstanding work could affect it.

## Decisions and reporting

Ask the human only for structural contradictions, missing or conflicting acceptance criteria that change scope, unreadable required artifacts, a missing workspace, an unresolved subthread launch after safe checks, or missing authority required by the selected workflow or an assigned external action. An unassigned or unauthorized PR may be omitted without blocking local plan completion; request PR authority only when the assignment requires it. For ordinary choices, use the least-expansive interpretation and record assumptions. Respect previously granted authorization and applicable higher-priority requirements.

Report each task’s implementation diff and base SHA, accepted task commit or exact reviewed uncommitted diff, tests and results, findings, assumptions and blockers; include plan PR, integration and cleanup results when applicable. Do not report completion without the required plan, spec, final reviewed task states, workspace and review evidence.
